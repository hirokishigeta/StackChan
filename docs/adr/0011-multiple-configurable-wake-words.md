# ADR-0011: 複数・ダッシュボード設定可能なウェイクワード

- Status: Accepted
- Date: 2026-06-14
- 関連: docs/design-spec.md §8 / §10 / §11.6 / ADR-0009

## コンテキスト

ウェイクワード（合言葉）はこれまで `WakeWordConfig` に複数登録できる構造を持っていたが、
新規デバイスのデフォルトが空リストで、ダッシュボードからの編集 UI もなく、入力バリデーション
（空フレーズ・感度の範囲）も存在しなかった。

実際のウェイクワード検出は CoreS3 側の esp-sr（WakeNet / MultiNet）で行う（design-spec §8.3）。
バックエンドの役割は「設定値の保存と配信」に限られ、デバイスは `GET /api/bot/{device_id}/wakeword`
で有効なリストを取得する。バックエンド側に検出器を新設はしない。

## 決定

- `WakeWordConfig` を 1 デバイスあたりの複数ウェイクワードのリストとして確定する。各エントリ
  （`WakeWordEntry`）はフレーズ・有効フラグ・感度 `threshold`（0〜1）を持つ。
- ドメイン値オブジェクトで自己検証する: 空（空白のみ含む）フレーズと範囲外の `threshold` を
  `__post_init__` で `ValueError` にする。`PUT /api/settings/{device_id}` はこれを HTTP 422 に
  マッピングする（ロード経路の寛容なフォールバックとは分離。design-spec §13）。
- 新規デバイスには編集可能な妥当なデフォルトリストを与える（ドメイン定数 `DEFAULT_WAKE_WORDS`）。
- ダッシュボードに「ウェイクワード」タブ（teal/green アクセント）を追加し、行の追加 / 削除で
  複数ワードを編集できるようにする。永続化は既存のデバイス設定 JSON API 経由（他パネルと同様）。
- 検出はデバイス側（esp-sr）のままとし、バックエンドは保存・配信に徹する。

## 検討した選択肢

- 選択肢 A: バリデーションを API スキーマ（Pydantic）だけで行う。
  メリット: 実装が局所的。デメリット: ドメインモデルが不正値を持ててしまい、不変条件が
  プレゼンテーション層に漏れる。クリーンアーキテクチャの方針に反する。
- 選択肢 B（採用）: 不変条件をドメイン値オブジェクトに置き、ルートで 422 に変換する。
  メリット: ドメインが常に正しい状態を保証。永続化ロード経路は寛容（既存方針）と両立。

## 理由

ウェイクワードの正当性（非空フレーズ・感度範囲）はビジネスルールであり、ドメインに属する。
既存の enum 検証（`validate_enum_inputs`）と同じく、ユーザー入力は厳格・ロードは寛容という
design-spec §13 の方針に沿う。

## 影響

- 新規デバイスのデフォルト `wake_words` が空から既定リストに変わる（`/wakeword` が空でなくなる）。
- `PUT /api/settings` が空フレーズ・範囲外感度・必須キー欠落で 422 を返すようになる。
- フォローアップ: firmware 側で `/wakeword` のリストを esp-sr のモデル / 閾値へ反映する実装は
  別タスク（本 ADR の範囲外）。

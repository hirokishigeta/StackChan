# ADR-0021: TTS を文単位でストリーミング合成・送出する

- Status: Accepted
- Date: 2026-06-14
- 関連: ADR-0010 (firmware audio) / docs/design-spec.md §7 / 旧 #7-b 実装

## コンテキスト

返答全文を1回で合成し、1本の Opus ストリームとして送出していた。ペルソナ（メイド）の返答が長文化したことで以下が顕在化した：

- **発話が「もはや言葉になっていない／とぎれとぎれ」**: 長文(20〜30秒)の連続再生中、デバイス(CoreS3)のデコード／再生がCPU逼迫で追いつかず、デコードキュー満杯時にフレームが捨てられ音声が破綻。
- **画面のテキストはみ出し**: 長文を1つの `sentence_start` で送るため、全文が画面からはみ出す。
- **長文の途中切断**: 単一の巨大再生が ws ping タイムアウト等に当たりやすい（ADR の ws-ping 対処と別に、そもそも巨大再生を作らない方が頑健）。

## 決定

返答を**文単位に分割し、文ごとに合成・送出**する。

- `_split_sentences`: `。．！？!?` と改行を境界に分割（ASCII の `.` は小数点等の誤分割回避のため境界にしない）。
- `_stream_reply`: 文ごとに `sentence_start`(その文のテキスト) → 音声フレーム送出。**次の文を現在の文の再生中にワーカースレッドで先読み合成**してギャップを抑える。リードインの無音ブリッジは最初の文だけ（再生開始時のクリップは一度きり）。
- 1文の合成失敗はその文だけテキストのみにフォールバック。
- メッセージ列は従来と後方互換（単文返答では `sentence_start` は1つ）。

## 検討した選択肢

- 選択肢 A（採用）: 文単位＋次文先読みストリーミング。チャンクが短くデバイス負荷・バッファに余裕、表示は1文ずつ、最初の声が早い。
- 選択肢 B: 全文一括のまま、デバイス側の再生バッファ／CPU対処（AFE停止等）。ファーム改修が必要でリスク大、表示はみ出しは別途対応要。
- 選択肢 C: 固定バイト長でチャンク分割。文境界を無視するため発話が不自然・表示も中途半端。

## 理由

文単位は「発話破綻・表示はみ出し・巨大再生による切断」を一度に緩和でき、バックエンド完結で実機フラッシュ不要。先読みで文間ギャップも最小化できる。

## 影響

- 1ターンで複数の `sentence_start` が流れる（xiaozhi の元設計通りデバイスは対応済み）。
- 文間に微小な無音が入りうる（先読みが間に合わない極端に短い文の場合）。デバイスの再生バッファ(約960ms)が吸収する想定。
- フォローアップ: 1文でも長すぎる場合の表示折り返し／スクロールは firmware 側の別課題。

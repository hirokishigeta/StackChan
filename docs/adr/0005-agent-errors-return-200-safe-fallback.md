# ADR-0005: Agent 実行時のエラーは HTTP 5xx ではなく 200 + 安全フォールバック応答で返す

- Status: Proposed
- Date: 2026-06-12
- 関連: docs/design-spec.md §11.3 / §11.7 / §13（安定性）, docs/backend-api.md §10, ADR-0001, ADR-0004

## コンテキスト

backend の Agent エンドポイント（`POST /api/agent/chat`・`POST /api/agent/proactive`）は、外部の Agent バックエンド（OpenAI 互換 API 等）へ HTTP で問い合わせる。この呼び出しはタイムアウト・接続失敗・非 2xx 応答・不正な JSON body など、外部要因で失敗しうる。

firmware（CoreS3）は会話ループの中でこの API を同期的に呼ぶ。design-spec §13 の安定性要件は「バックエンド未起動 / API タイムアウト時に落ちない」「音声認識失敗時に会話ループが壊れない」を求めており、Agent 失敗も同様に 1 ターンの失敗で会話ループ全体を壊してはならない。

API がエラーを HTTP 5xx で返すと、firmware 側は HTTP ステータスごとのエラー分岐・リトライ・フォールバック表示を都度実装する必要があり、実装漏れがあると会話が停止する。AgentGateway の ABC は transport 固有例外を `AgentError` に包んで返すコントラクトを既に持つ（`application/ports/agent_gateway.py`）。

## 決定

Agent 実行中に `AgentError` が発生した場合、backend は **HTTP 5xx を返さず、HTTP 200 + 安全フォールバック応答** を返す。

- フォールバックは中立的・非破壊的な定型応答（固定文 + `emotion="sad"` + `set_expression` アクション）とし、`AgentChatResponse` と同一スキーマで返す。
- 失敗は warning ログに残す（device_id 付き）。レスポンスに transport 固有のエラー詳細は載せない。
- chat / proactive の両エンドポイントに同方針を適用する。
- 実装箇所は `interfaces/api/agent_routes.py`（`AgentError` を捕捉してフォールバックに写像）。

## 検討した選択肢

- A: 200 + 安全フォールバック応答（採用）
  - メリット: firmware は成功時と同じ応答形を 1 経路で扱えばよく、会話ループが途切れない。安定性要件（§13）に直接合致。エラー分岐の実装漏れに強い
  - デメリット: HTTP セマンティクス上は「失敗を 200 で返す」ことになり、監視・デバッグ時にステータスコードだけでは失敗を判別できない（ログ・将来のメタフィールドで補う）
- B: 5xx（例: 502/504）を返す
  - メリット: HTTP セマンティクスに忠実。失敗がステータスコードで明確
  - デメリット: firmware 側にエラーハンドリング/フォールバックを必須化し、実装漏れで会話ループが停止する恐れ。§13 の「落ちない」要件をクライアント実装に依存させてしまう
- C: 200 で返すがフォールバック文ではなくエラーフラグのみ返す
  - メリット: クライアントが失敗を明示的に判別できる
  - デメリット: 結局 firmware 側に「フラグ時の振る舞い」を実装させる必要があり、B と同種の漏れリスクが残る

## 理由

backend を「AI に身体を与える」端末（ADR-0001）の安定したバックエンドと位置づける以上、単一ターンの外部失敗で端末側の会話体験を壊さないことを最優先とする。安定性をクライアント実装の正しさに依存させず、backend 側で吸収する方が堅牢である。HTTP セマンティクスの厳密性より、§13 の非機能要件（安定性）を優先した。

## 影響

- firmware は Agent 応答を常に 200 + `AgentChatResponse` 形として扱えばよい（エラー専用分岐が不要）。
- 監視・運用では HTTP ステータスだけで Agent 失敗を検知できないため、ログ（warning）に依存する。将来、フォールバックか否かを示すメタフィールド追加やメトリクス計上を検討する余地がある（フォローアップ）。
- バリデーションエラー（422）や未登録 device（404）など Agent 実行前のエラーは本方針の対象外で、通常どおりのステータスを返す。
- 本方針は design-spec §11.3 / §11.7 / §13 と `docs/backend-api.md` §10 に反映済み。Phase 4 実装のレビューをもって Accepted にする。

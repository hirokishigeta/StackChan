# ADR-0014: バックエンド側ウェイクワード・ゲート（STT テキストマッチ）

- Status: Accepted
- Date: 2026-06-14
- 関連: docs/design-spec.md §8 / ADR-0011（複数ウェイクワード）/ docs/backend-protocol.md §6（VAD）

## コンテキスト

ADR-0011 ではウェイクワード検出をデバイス側（esp-sr / WakeNet）で行う前提だった。
しかし WakeNet は登録できるモデルが限られ、任意の日本語フレーズを自由に設定できない。
ユーザーが「ねえスタックチャン」など任意のウェイクワードを使えるようにするには、
デバイスは音声を連続ストリーミング（VAD で発話区切り）し、バックエンドが
「いつ会話に入るか（engage するか）」を判定する方式が必要になる。

バックエンド側には既に ASR（STT）パイプラインと、デバイスごとの
`BotSettings.wake_word`（有効なウェイクワード一覧）がある。追加のウェイクワード用
モデルを持ち込まずに、STT が起こしたテキストに対する文字列マッチでゲートできる。

## 決定

WS 音声ループにバックエンド側ウェイクワード・ゲートを追加する。

- デバイスは連続ストリーミング（VAD ゲート）する前提。バックエンドが engage 判定を行う。
- `_finalize_turn` で ASR がテキストを得た**後**・`_run_agent_turn` の**前**にゲートを評価する。
- 判定はドメインの純粋関数 `matches_wake_word(text, words)` で行う。両辺を正規化
  （NFKC + casefold + 空白・記号除去）し、ウェイクフレーズが認識テキストの部分文字列なら一致。
- 未 engage 時: 一致したら engage して全文をそのままエージェントへ渡す（LLM が処理）。
  不一致なら `{"type":"tts","state":"stop"}` を送って return（環境音・独り言は無視）。
- engage 済み時: 最後の処理からの経過がアイドルタイムアウト（`wake_idle_timeout_ms`）以内なら
  ウェイクワード無しでも処理を継続。超過していたら disengage 扱いで未 engage と同じ判定に戻す。
- engage / アイドル計測の時刻は `asyncio.get_running_loop().time()`（イベントループの単調時計）を使う。
  壁時計（time-of-day）は使わない。
- `reply.end_conversation` で listen stop する際に disengage、`listen start` のたびに un-engage に戻す。
- 設定 `wake_word_gate_enabled`（デフォルト `False`）でガード。OFF の間は従来の
  オンデバイス・ウェイク挙動と完全に同一（ゲート無し）。ファームが連続ストリーミング対応するまで OFF。

## 検討した選択肢

- 選択肢 A: バックエンドにウェイクワード検出モデル（音声）を追加。
  - メリット: 音声のまま判定でき、誤認識テキストに依存しない。
  - デメリット: モデル選定・任意日本語対応・推論負荷・依存追加が必要。重い。
- 選択肢 B（採用）: STT テキストへの文字列マッチでゲート。
  - メリット: 既存の ASR と設定だけで実現、任意の日本語フレーズ対応、追加モデル不要。
  - デメリット: STT の誤認識に弱い。部分文字列マッチのため過検出の余地。

## 理由

「任意の日本語ウェイクワード」を最小コストで満たせる。既存パイプライン（ASR）と
デバイスごとの設定をそのまま使え、新たな重い依存やモデルを持ち込まない（CLAUDE.md）。
デフォルト OFF にすることで、ファームの連続ストリーミング対応が整うまで現行挙動を一切変えない。

## 影響

- 設定 `wake_word_gate_enabled` / `wake_idle_timeout_ms` を `config/settings.py` に追加。
- ビジネスロジックはドメインの純粋関数に閉じ込め、プレゼンテーション層（WS ハンドラ）は
  ゲートの可否だけを問い合わせる（CLAUDE.md のレイヤー規約）。
- フォローアップ: ファームを連続ストリーミング（オンデバイス・ウェイク無効）に切り替えた上で
  ゲートを ON にする。STT 誤認識による取りこぼし／過検出はしきい値や正規化の調整で対応。
